## 실행

```bash
cd /Users/max/noncelab/center/bitcoin-center-seoul
export PATH="/opt/homebrew/opt/node@22/bin:$PATH"
node --version
git status --short --branch

```

프로젝트 Node는 22.x, 브랜치는 `redesign/center-web`이어야 한다. Git 상태가 깨끗하지 않은 것은 이전 작업 파일이 남아 있기 때문이다. 초기화하거나 미추적 파일을 삭제하지 않는다. 다른 브랜치나 예상 밖 변경이 보이면 먼저 그 상태를 확인한다.

## 아래 본문을 첫 메시지로 붙여 넣기

```text
Bitcoin Center Seoul 개편 작업을 이 Codex 세션에서 이어가줘.

대상 저장소는 /Users/max/noncelab/center/bitcoin-center-seoul이고 작업 브랜치는 redesign/center-web이야. /Users/max/saturdayblock-web은 참고 프로젝트이지 개편 대상이 아니야.

먼저 아래 인수인계 문서를 부록까지 끝까지 읽어줘.
docs/handoff/2026-09-08-codex.md

이 문서에는 원본 사용자 메시지 33개, 15개 질문과 답변의 승인 범위, 마지막 TODO 10개, 그 이후의 디렉터리 구조 요청, 하위 작업 11개, 실제 부분 구현, 검사 이력, 미정 사항, 원본 로그와 메모리의 절대 경로가 들어 있어. 긴 파일의 읽기 결과가 잘리면 이어 읽어. 중간의 완료된 연구 TODO를 마지막 디자인 TODO로 착각하지 마.

AGENTS.md와 web/AGENTS.md도 읽고, web/DESIGN.md는 인수인계 문서의 정정 사항과 함께 확인해줘. 이 저장소에서는 ~/.agents/MY-DESIGN-STYLE.md를 적용하지 않는 Design Overrides가 있어. 오래된 animation-heavy/페이지 구성 미정 문구보다 이후 사용자 답변이 우선이야.

현재 작업은 기존 승인을 받은 공개 사이트의 첫 디자인 시안이야. 전체를 다시 처음부터 조사하거나 이미 답한 15개 질문을 반복하지 말고, 저장된 결과와 실제 코드를 확인한 뒤 미완료 작업부터 이어가줘. 구체적인 최종 디자인은 아직 승인하지 않았고, 공개 디자인을 보고 판단한 다음 백엔드·관리자·DB 이전 단계로 가는 순서야.

독립적으로 나눌 수 있는 일은 팀/서브에이전트를 적극 활용해서 병렬로 진행해줘. 처음에는 필요한 2~4개 정도로, 목표·산출물·수정 파일·완료 기준을 분명히 나눠. 같은 파일의 동시 수정과 같은 주제의 중복 조사를 피하고 총괄이 실제 결과와 검사 근거를 대조해줘. Codex에서 제공하는 기능으로 운영하되 OMO의 옛 팀이나 task ID가 자동으로 살아 있다고 가정하지 마.

원래 모델 운용 희망은 총괄 GPT-6 Astra, 중요 설계/진단 xhigh, 일반 구현 high, 명확한 반복 작업 medium이야. 실제 사용 가능한 모델과 effort를 확인해서 적용해줘. Grok Build는 제외하고 Claude Fable 5.1은 비용 때문에 필수로 가정하지 마. 모든 팀원에게 최고 설정을 일괄 적용하지 마.

중요한 요구사항:
- 웹만 봐도 센터에 와 본 것처럼 느끼고 실제로 방문하고 싶어야 해. 센터 소개, 밋업, 전시·체험, 교육, 활동 기록, 굿즈, 방문 안내가 명확해야 해.
- 시네마틱하지만 담백하고 따뜻한 갤러리 느낌. 모션은 매끄럽고 고급스럽되 과하지 않게. Impeccable/taste 등 필요한 스킬을 사용해서 AI 템플릿처럼 보이지 않게 해줘.
- 라이트 기본+다크 전환, 제공 로고의 오렌지·파랑, 한국어/영어와 해외 SEO가 필요해. 최종 로고/아이콘 파일과 정확한 색상값은 아직 확정하지 않았어.
- 실제 센터 사진을 사용해. DESIGN.md의 잘못된 사진 목록·영상 URL·MIT 라이선스 설명은 인수인계의 정정대로 다뤄줘. 외부 레퍼런스 사진을 센터 사진으로 쓰거나 행사·가격·재고를 지어내지 마.
- 폰트는 실제 한영 화면에서 후보를 비교해줘. 현재 Manrope/Noto는 후보이지 최종 승인이 아니야.
- SVG 관리안은 참고 프로젝트의 public/tailwind-svg와 public/bootstrap-icons-svg 운영을 보고 검토해줘. 두 폴더나 새 의존성을 무조건 복사하라는 뜻은 아니야.
- 프로젝트 디렉터리도 유지보수·리팩토링하기 좋게 구조화해줘. 이 마지막 요청은 원문에는 있지만 옛 TODO에는 아직 추가되지 않았으니 반드시 현재 목록에 넣어줘.
- 보안·세션·인증이 최우선이야. 개발 중 주기적으로 로컬 보안 감사를 하고, 결제·권한·DB 변경은 중복 요청·지연 알림·장애·동시 실행 같은 실패 경로도 실제 검증해야 해.
- 향후 회원/비회원 허용과 예약 운영 방식은 관리자에서 선택 가능해야 하고, KRW 고정과 BTC 고정 가격 모두 필요해. 초기 마스터 1명이 일반 관리자를 만드는 구조, 알림은 이메일. 라이트닝은 확정이지만 토스 원화 수납은 미정이야. 세부 승인/미정 경계는 문서의 15개 답변을 따라줘.

금지 사항:
- GitHub Actions는 절대 사용하지 마. .github/workflows/deploy.yml.disabled를 그대로 보존하고 삭제하거나 다시 활성 확장자로 바꾸지 마.
- 운영 데이터 변경, 실제 결제/환불/메일, 배포, 커밋·병합·파괴적인 Git 명령은 따로 승인 없이 하지 마. upload-to-ec2.sh는 운영에 실행하지 마.
- 루트 레거시 src/·Express·SQLite·업로드와 필요한 URL/기능을 보존해. /walletExperence는 리다이렉트 없이 없애지 마.
- npm과 package-lock.json을 사용해. 이 프로젝트에 Bun을 도입하지 마.
- 다른 작업자의 변경, 미추적 web/, 중단된 담당이 남긴 부분 코드를 함부로 원복하거나 삭제하지 마.
- 테스트를 지우거나 약하게 만들거나 검사 오류를 숨겨서 통과했다고 하지 마.

우선 실제 상태를 대조해줘. web/는 완성 홈페이지가 아니라 부분 구현이야. 홈 locale page가 없고, 루트/locale layout이 중복 html/body를 출력하며, root-params 생성 타입과 개발 도구 matcher도 점검해야 해. 마지막 홈 테스트는 /ko에서 404로 실패했어. 이전 primitives 담당은 lost지만 코드와 하위 로그는 남아 있으니 재사용 가능한 부분부터 확인해줘.

Node 22를 사용해. 개발 서버는 web/에서 127.0.0.1:3100이고 Playwright 설정에는 webServer가 없어서 서버를 따로 준비해야 해. 아직 재실행하지 않은 검사나 과거 0 vulnerabilities/22 tests 결과를 현재 전체 통과라고 보고하지 마. 변경에 맞는 diagnostics, 타입, 린트, 브라우저, 빌드, 의존성/보안 검사를 로컬에서 수행하고 결과와 한계를 남겨줘.

첫 응답에서는 복구한 작업 단계, 남은 TODO, 병렬 담당과 파일 소유권, 바로 시작할 작업을 짧게 설명한 뒤 승인된 디자인 작업을 진행해줘. 결정이 필요한 부분은 해당 시점에 구체적으로 물어보고 나머지는 계속해줘.

완료한 단계마다 현재 TODO와 파일·검사 결과·남은 결정을 저장소의 체크포인트에 남겨서 세션이 다시 끊겨도 이어갈 수 있게 해줘. 인수인계 부록의 사용자 원문과 옛 TODO는 역사 기록으로 보존하고 현재 진행 상태는 별도로 갱신해줘.
```

## 재개 방식의 한계

이 프롬프트는 원본 OMO 세션을 Codex 세션 포맷으로 변환하지 않는다. 같은 작업 파일, 원문을 보존한 인수인계, 검증 증거를 읽어 이어가는 방식이다. 사용자가 별도 창에서 이 프롬프트를 보내기 전에는 새 구현 작업이 시작되지 않는다.
