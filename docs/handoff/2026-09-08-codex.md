## 2. 지시의 우선순위와 작업 경계

### 2.1 사용자 의도

성공 기준은 코드 생성량, 에이전트 수, 멋진 설명이 아니다. 기존 기능과 데이터를 보존하면서 실제 사용에서 개선을 검증해야 한다.

- 센터다운 새로운 웹 경험을 만든다. 단순한 색상 변경이나 기존 화면의 외형 수정에 그치지 않는다.
- 먼저 전체 구조를 넓게 파악하고, 핵심 경로와 변경 대상은 깊게 추적한다. 모든 파일을 무작정 읽거나 이미 끝난 조사를 반복하지 않는다.
- 문서와 현재 코드를 대조하고, 사용자 결정·에이전트 제안·소스에서 확인한 사실·실제 실행 결과를 구분한다.
- 유지보수와 리팩토링이 쉬운 구조로 작성한다. 근본 원인을 해결하되 불필요한 추상화, 중복 계층, 과도한 설계를 만들지 않는다.
- 사용자 결정이 필요한 사안은 해당 사안이 작업을 막는 시점에 바로 묻는다. 이미 승인된 15개 답변을 다시 처음부터 묻지 않는다.

### 2.2 확정된 금지 사항

1. GitHub Actions를 활성화·실행·생성하거나 검증·배포의 의존 조건으로 삼지 않는다.
2. `.github/workflows/deploy.yml.disabled`를 지우거나 다시 `.yml`/`.yaml`로 바꾸지 않는다.
3. 운영 DB, 실제 결제, 실제 환불 송금, 운영 이메일, SSH 배포를 디자인 단계에서 실행하지 않는다.
4. 배포, 병합, 커밋, 파괴적인 Git 명령은 이번 승인에 포함되지 않는다. 다른 작업자의 변경을 되돌리지 않는다.
5. 기존 `data/`, 업로드 파일, 게시된 URL과 필요한 동작을 보존한다. 특히 `/walletExperence`는 오타처럼 보여도 공개된 URL이므로 리다이렉트 없이 없애지 않는다.
6. `upload-to-ec2.sh`를 운영에 실행하지 않는다. `rsync --delete`가 운영 데이터와 업로드를 지울 수 있다.
7. 프로젝트에서는 npm과 `package-lock.json`을 사용한다. Bun으로 패키지 관리나 프로젝트 실행 방식을 바꾸지 않는다.
8. 참고 프로젝트의 다중 브랜드/판매자 범위, Vercel 전용 보안 기본값, 미해결 취약 동작을 통째로 복사하지 않는다.
9. 테스트를 지우거나 약하게 만들거나, 오류를 숨겨서 통과했다고 보고하지 않는다. 에이전트 완료 보고만으로 구현·검증 완료를 판정하지 않는다.

### 2.3 디자인 지침 충돌 해소

루트 `AGENTS.md`의 `## Design Overrides`는 `~/.agents/MY-DESIGN-STYLE.md`를 이 저장소에 적용하지 말라고 명시한다. 일반 스킬이 그 전역 스타일을 요구해도 이 프로젝트의 예외와 사용자의 새 디자인 방향을 우선한다.

같은 파일 하단의 “animation-heavy”, “one-page vs multi-page undecided”는 초기 상태의 기록이다. 이후 사용자는 **과하지 않은 매끄러운 모션**과 **여섯 영역의 페이지 구성**을 승인했다. 과거 표현을 근거로 결정을 되돌리지 않는다.

`web/DESIGN.md`는 에이전트가 작성한 **첫 후보의 작업 문서**이며 사용자 최종 승인서가 아니다. 이 문서 4절의 사진·영상·라이선스 정정과 폰트 미확정 상태를 함께 적용한다.

## 4. 디자인·콘텐츠·추가 요청

### 4.1 사용자가 원하는 경험

- 웹만 봐도 센터에 와 본 것처럼 느끼고, 실제로 방문하고 싶어지는 사이트.
- 센터의 목적, 공간, 활동, 방문 방법을 명확하게 설명한다. 몰입감 때문에 소개가 사라지면 안 된다.
- 밋업, 전시, 교육 현장, 굿즈가 제대로 드러나야 한다.
- 시네마틱하지만 담백하다. 과장되고 느끼한 문구나 차갑고 날카로운 박물관 인상은 피한다.
- 갤러리 같은 정제된 배치에 실제 사람과 활동의 따뜻함을 유지한다.
- `btchouse.kr`을 크게 넘어서는 디자인 품질을 목표로 한다. 수상 여부나 객관적 우월성이 검증됐다고 표현하지 않는다.
- 모션은 매우 부드럽고 고급스럽되 과하지 않게 한다. 키보드, 터치, 작은 화면, reduced motion에서도 핵심 콘텐츠와 조작이 살아 있어야 한다.
- 한국어/영어 전환뿐 아니라 국제 노출과 실제 SEO가 중요하다. 서버 콘텐츠, locale URL, 문서 언어, 메타데이터, canonical/hreflang, 공유 이미지, sitemap 등을 설계해야 한다. 첫 로컬 시안은 noindex, 공개 전 검색 정책을 별도로 점검한다.

### 4.2 레퍼런스와 스킬의 승인 범위

- 사용자는 사용 가능한 스킬·플러그인, 팀 모드, 병렬 작업, 서브에이전트 활용을 명시적으로 허용했다.
- Impeccable, taste 계열을 써서 AI 템플릿처럼 보이지 않는 디자인을 원한다. 로컬 후보는 `~/.agents/skills/frontend-design/`, `design-taste-frontend/`, `animate/`, `adapt/`, `typeset/`, `critique/`이며 필요할 때 해당 `SKILL.md`를 읽는다. 원래 OMO의 frontend/visual-qa 안내도 참고할 수 있지만 Codex에 동일 도구가 있다고 가정하지 않는다.
- awesome-design-md 탐색 요청은 보존한다. 원본의 철자는 “awesome desgin md”이며 특정 저장소 URL을 지정한 것은 아니다. 이미 검토한 자료와 근거를 확인한 후 부족한 부분만 보완한다.
- Open Design Cloud 또는 Local Codex를 통한 시안 탐색은 논의된 선택지다. 특정 생성 도구·특정 시안을 최종 선택한 것으로 해석하지 않는다.
- Runway의 미디어 배치, Airbnb의 접근하기 쉬운 탐색, 문화공간·갤러리 사례는 에이전트의 부분 참고 제안이다. 브랜드, 색상, 사진을 그대로 가져오지 않는다. Mastercard는 이전 조사에서 검증하지 못했다.
- `.omo/design-refs/index.html`과 `.omo/design-refs/mockup/index.html`은 존재한다. 과거 비교 자료·탐색용 HTML이지 승인된 새 홈페이지가 아니다. 이전에는 현대카드 라이브러리, 피크닉, 코사이어티 등 문화공간을 살폈고 Bitcoin House Bali의 따뜻한 분위기에 관심을 보였으나, 특정 사이트 복제 승인은 없었다.
- 이미지 생성은 이전에 두 번 `400 Argument not supported: size`로 실패했다. 생성된 콘셉트가 완성돼 있다고 보고하지 않는다. 실사와 실제 브라우저 화면을 활용한다.

### 4.3 마지막 추가 요청: 폰트, SVG, 디렉터리

**폰트:** 사용자가 따로 비교·검토를 요청했다. 현재 `web/src/app/[locale]/layout.tsx`에는 Manrope와 Noto Sans KR가 들어 있지만, 이는 후보이며 최종 선택이 아니다. 한글/영문을 실제 화면에서 비교하고 가독성, 로딩, 분위기의 근거를 제시한다. 과거 `@fontsource-variable/pretendard` 조회는 E404였다. 이 실패를 모든 Pretendard 사용 방법이 불가능하다는 뜻으로 확대하지 않는다.

### 5.5 레거시와 데이터 보존

루트 앱은 Vite/React 18 + Express + better-sqlite3이고, 새 앱은 `web/`다. 루트 `npm run dev`와 `web/`의 같은 이름 스크립트는 다른 앱을 실행한다.

루트 `AGENTS.md`의 기능 지도와 `src/components/AGENTS.md`를 해당 코드 작업 전에 읽는다. 핵심 보존점:

- 공개 랜딩, 행사/하이라이트, 관리자 인증·편집·이미지 업로드, 지갑 체험.
- 런타임 SQLite는 `data/events.db`; 루트 `events.db`는 런타임 DB가 아니다. `database.js` import가 DB를 만들 수 있으므로 읽기 전용 조사에서 실행하지 않는다.
- 현재 업로드와 기존 URL·날짜 형식을 보존한다. 새로운 DB 이전 때 실제 데이터, 업로드 참조, 백업과 복구를 함께 검증한다.
- 현 PM2 파일은 `ecosystem.config.cjs`; `.js` 중복 파일을 활성 파일이라고 수정하지 않는다.
- `deploy.sh`와 `DEPLOY.md`의 설명은 서로 다를 수 있다. 새 수동 배포 절차는 운영 환경을 따로 확인하고 승인받는다.

## 7. 팀·서브에이전트 인수인계

### 7.1 사용자 작업 방식

독립 작업은 필요한 2~4개 정도로 병렬 분담한다. 화면·UX, 서버·DB, 인증·결제, 테스트·운영이 원래 제시된 분할 예다.

- 각 담당의 목표, 산출물, 수정 가능한 파일·모듈, 끝나는 조건을 명시한다.
- 같은 주제의 중복 조사와 같은 파일의 동시 수정을 피한다.
- 총괄이 결과의 모순을 대조하고 실제 결과물을 검사한다.
- 일반 구현 high, 명확한 반복 작업 medium을 고려한다. 초기 진단/중요 설계 xhigh, 결제·권한·DB 이전은 강한 추론과 실패 경로 검증을 적용한다.
- 원래 총괄 모델 희망은 GPT-6 Astra다. Grok Build는 제외한다. Claude Fable 5.1은 비용 때문에 필수로 가정하지 않으며 필요한 설계/디자인 추가 검토에 한정한다.
- Codex CLI의 실제 사용 가능한 모델·effort·서브에이전트 기능에 맞춰 적용한다. 존재하지 않는 설정 이름을 만들거나 모든 담당에 최고 모델/effort를 일괄 배정하지 않는다.
- 사용자는 이전 별도 상담에서 Claude 중심/Codex 중심의 전환 가능한 두 구성에 관심을 보였다. 이는 보존할 운영 선호이며, 이번 사이트 재개의 조건으로 전역 OMO 설정 두 벌을 새로 만들라는 지시는 아니다.

가능한 첫 분담: 총괄은 locale·홈 통합과 최종 검증, 담당 A는 프리미티브 동작 점검, 담당 B는 폰트/SVG 비교안, 담당 C는 실제 사진·콘텐츠 구성. 파일 소유권을 먼저 정하고, 현재 디자인 단계와 무관한 결제/DB 구현 팀은 시작하지 않는다.

### 8.2 오해하면 안 되는 기능

- 제공자 타입에 btcpay/blink/both/zaprite가 있어도 현재 관리자 설정은 Blink/both 신규 선택을 막는다. 타입 이름만 보고 전부 지원 대상으로 복사하지 않는다.
- `showAuthButtons`는 표시 설정일 뿐 서버 회원 전용 정책이 아니다.
- meetup의 `approvalStatus`는 행사 게시물 승인이지 참가자 신청 승인제가 아니다. 대기 명단/대관 모델도 조사된 경로에서는 찾지 못했다.
- 현장 수령은 모델/API 기반은 있지만 공개 checkout과 상품별 허용 검증이 완성됐다고 볼 수 없다.
- 원화 고정·비트코인 고정 가격은 둘 다 있다. 조사한 결제 경로에는 토스 원화 수납 구현이 없었다.
- `refundOrderSafely`는 회계·재고 정리이며 실제 외부 송금 함수가 아니다.
- 공개 환불 정책은 소스의 `lib/legal`을 사용하며 편집 가능한 `SiteSettings.refundPolicy`와 같다고 단정하면 안 된다.
- 참고 프로젝트는 추가 마스터 생성도 허용할 수 있지만 센터 요구는 초기 마스터 1명 → 일반 관리자 생성이다.

### 8.3 재사용 전에 해결·재검증할 소스상 위험

1. LNURL 관리자 등록 경로는 전역 등록 비밀값을 사용하며 기존 마스터 세션을 요구하는 암호 등록 경로와 다르다. 암호/비밀값 메타데이터가 단기 JSON 인증 기록에 저장되는 경로도 있다. 해당 등록 경로를 그대로 이식하지 않는다.
2. `lib/two-factor-secret.ts`는 암호화 설정 부재/실패 시 평문 반환 분기가 있다. 정상 운영 시작의 ENCRYPTION_KEY 검증과 별개로 함수 계약을 안전하게 만들어야 한다. 운영에서 실제 평문 저장됐다고 입증된 것은 아니다.
3. BTCPay meetup webhook에서 취소된 예약이 `pending_confirmation`으로 바뀔 수 있는 소스 경로가 관찰됐다. 최종 상태와 지연 이벤트 정책을 먼저 통일한다.
4. 일부 운영 보안 기본값이 `NODE_ENV` 대신 `VERCEL_ENV=production`에 의존하고, KV 부재 시 관리자 폐기 정보가 프로세스 메모리로 내려간다. AWS에서 공유·영속 폐기와 fail-closed 설정을 명시한다.
5. 일반 사용자 tokenVersion 검사는 최대 60초 오래될 수 있고 관리자 검사는 새 DB 상태를 확인한다. 세션 발급과 등록이 항상 함께 성공하는지도 별도 점검한다.
6. 예전 `expireOldPayments` 작업은 Blink 중심 외부 확인과 동시 처리 후 상태 덮어쓰기 위험이 있다. 새 cron 구성과 구형 함수를 구분한다. 운영 활성 여부를 소스만으로 단정하지 않는다.
7. 외부 invoice 생성과 로컬 저장은 별개다. 중간 실패·중복 요청·재전송·지연 webhook·금액 불일치·재고/좌석 경합을 명시적인 테스트로 검증한다.
8. 참고 보안 워크플로우에는 advisory 예외·비차단 감사와 비활성 CodeQL/Trivy가 있었다. 일부 검사 통과를 취약점 0개나 인증 안전성 인증으로 표현하지 않는다. 센터에서는 로컬 검사로 적용한다.

- 결제/예약/재고 변경: 중복·지연·재전송, 처리 중 실패, 동시 좌석/재고 요청, 금액 일치, 취소 후 늦은 성공 알림, 외부 invoice와 로컬 상태 불일치.
